# 基于解析器语法期望和语法作用域构建补全

`pg-parser` 继续作为严格的原始解析树解析器；`pg-completion` 返回补全专用上下文，其中包含强类型语法期望、对象意图、替换范围和尽力而为的查询作用域。解析器在补全点暴露强类型语法期望，但残缺 AST 和 Catalog 对象都不能跨越这条接缝；`pg-completion` 从 Token 流推导作用域，再由调用方拥有的适配器结合元数据解析上下文。该设计避免使用字符串表示语法规则，并使解析器正确性不依赖编辑器容错逻辑。

## 考虑过的方案

- 不暴露残缺的原始解析树，因为那会迫使每个 AST 使用方理解缺失的必选子节点。
- 不由 `pg-completion` 根据邻近 Token 推断全部语法期望，因为这会在解析器之外复制 PostgreSQL 的语法决策。
- 不在 `pg-parser` 内解析 Catalog 对象，因为解析和元数据具有不同的依赖、失败模式和生命周期。

## 影响

语法产生式必须在收集点显式发布可选 Token 和具名语法槽位。所有由顶层语句分派入口支持的语句最终都必须覆盖 collect 模式；新增或扩展产生式时，必须同步添加 collect instrumentation 和覆盖场景。`ExpectationSet` 只表达候选，不编码实现进度或恢复状态；空集合表示当前位置没有语法候选，恢复问题由 `CompletionRecovery` 表达，覆盖遗漏由测试门禁发现。

所有语句都必须具备关键字和子命令边界的结构覆盖，只有引用 Catalog 名称的位置才需要对象槽位覆盖，也只有具有关系可见性的语句才需要非空查询作用域。作用域收集刻意采用尽力而为且仅包含语法信息的方式；元数据查询、权限、排序和 LSP 位置转换仍由调用方负责。

补全候选使用无 Catalog 的声明式 YAML 场景测试：输入内嵌补全点，期望值精确列出 Token 和语法槽位候选。具体对象名称、插入文本和展示字段属于 adapter 产生的补全项，不进入该模块的候选基线。
